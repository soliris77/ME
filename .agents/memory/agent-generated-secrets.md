---
name: No agent-side path to store an agent-generated value as a true secret
description: What to do when a feature (e.g. Web Push) needs a private key generated by the agent, not supplied by the user.
---

Some features (e.g. Web Push notifications) require a keypair or credential generated
locally by the agent (VAPID keys, signing keys, etc.), not one the user types in.

**Why:** `requestSecrets` is designed to collect values the *user* provides interactively — it
has no mode for the agent to hand over a value it just generated and have it stored as a real
secret. `setEnvVars`/environment-variable tools will store it, but only as a plain, non-secret
env var — visible in the environment, not encrypted-at-rest like a secret.

**How to apply:** before implementing a feature that needs an agent-generated private credential,
surface this tradeoff to the user explicitly rather than silently storing it as a plain env var.
Options: (a) ask the user to generate the keypair themselves and paste the private half through
`requestSecrets`, (b) accept it as a non-secret env var and flag that tradeoff, or (c) trim the
feature's scope to avoid needing a private key at all. Don't default to (b) without asking.
